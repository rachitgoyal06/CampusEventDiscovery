01 • PROBLEM STATEMENT & USE CASE SLIDE 1 / 7
Connecting Students & Campus Life
Solving event fragmentation and unmanaged registration workflows.

⚠️ Real-World Problem

Event notices in universities are scattered across unorganized WhatsApp chats, physical posters, and disconnected Google Forms. Students miss deadlines, venues overflow, and coordinators struggle with duplicate entries.

👥 Intended Users

Students: Discover verified technical, cultural, and sports events; register with official @muj.manipal.edu accounts.
Faculty & Admins: Publish events, track live capacities, and export attendee lists.

🎯 Realistic Use Case

A student searches for upcoming hackathons, discovers Cyber Mafia & Code Of The Seas, verifies venue and capacity details, clicks "Register", and immediately receives an authenticated digital event pass.

📌 Core Project Objective

"To engineer an OOP-driven centralized event platform that streamlines discovery, eliminates duplicate registrations, and automates real-time campus event management."

02 • OBJECT-ORIENTED DESIGN SLIDE 2 / 7
Architecture & The 4 OOP Pillars
Structuring robust campus entities through core object-oriented principles.

🔒 Encapsulation

All model fields (userId, eventName, capacity) are private with controlled public getters/setters. Sensitive DB config is hidden.

🧬 Inheritance

Student extends User and Admin extends User. Child classes reuse identity attributes and chain constructors via super(...).

🎭 Polymorphism

Overriding: Subclasses override displayUser() for specialized output.
Overloading: Default & parameterized constructors in Event, User.

🧩 Abstraction

interface Registrable outlines registration contracts without leaking SQL/JDBC implementation. DAO layer isolates DB logic.

📐 Class Relationship Overview

User (Superclass) ← [Inherits] Student & Admin | Registrable (Interface) ← [Implements] RegistrationDAO | Registration associates User & Event

03 • CORE JAVA CONCEPTS USED SLIDE 3 / 7
Enterprise Java Implementation
Technologies and Java language constructs powering the system.

📦 Packages & Access Modifiers

  • Modular package architecture: model, dao, interfaces, util.
  • Strict encapsulation with private, public, static, and final constants.

🛡️ Exception Handling

  • Robust try-catch-finally and try-with-resources preventing JDBC connection leaks.
  • Defensive null checks on unscheduled events (e.g. rs.getDate() != null).

📚 Collections & Generics

  • List<Event> & ArrayList for dynamic event records.
  • Set<Integer> for O(1) duplicate registration validation.
  • Map<String, String> for REST payload mapping.

🔌 JDBC & PostgreSQL Cloud Driver

Uses postgresql-42.7.13.jar to establish pooled SSL connections to Supabase PostgreSQL, executing parameterized PreparedStatement queries to guarantee SQL-injection immunity.

04 • PROGRAM FLOW & IMPLEMENTATION SLIDE 4 / 7
Execution Flow & Code Walkthrough
How user requests traverse through interfaces, DAOs, and database.

🔄 Request Pipeline

1. Input: User triggers action on UI/CLI.
2. Dispatch: REST Handler verifies authentication token.
3. DAO Layer: DAO opens connection via DBConnection.
4. Persistence: Parameterized query executed on PostgreSQL.
5. Output: Hydrated objects serialized into JSON/ticket pass.

💡 Key Design Pattern

Data Access Object (DAO) Pattern completely separates domain models from storage mechanisms, ensuring high cohesion and low coupling.

// Inheritance & Constructor Chaining
public class Student extends User {
    private String studentId;
    private String course;

    public Student(int userId, String name, 
                   String email, String password, 
                   String studentId, String course) {
        super(userId, name, email, password, "STUDENT");
        this.studentId = studentId;
        this.course = course;
    }

    @Override // Runtime Polymorphism
    public void displayUser() {
        System.out.println("Student: " + getName() 
            + " | Course: " + course);
    }
}
05 • APPLICATION DEMONSTRATION SLIDE 5 / 7
Key Feature Demonstrations
Live workflows demonstrated across student and administrative roles.

1️⃣ Student Authentication

Input: Student inputs credentials.
Processing: Enforces @muj.manipal.edu email domain; verifies password hash; hydrates Student object.
Output: Personalized student dashboard with ticket pass access.

2️⃣ Discovery & Booking

Input: Filters by Category ("Technical") or searches "Cyber".
Processing: Real-time filtering; executes registerForEvent(userId, eventId).
Output: Instant "✓ Registered" state; decrements available capacity.

3️⃣ Admin Event Control

Input: Admin creates or deletes campus events.
Processing: Checks role.equals("ADMIN"); handles null dates safely; executes transactional cascading delete.
Output: Event catalog updates across all connected clients.

🔗 Object Collaboration in Action

When booking: Student → calls RegistrationDAO → inserts into DB → instantiates Registration record → reflects on student pass.
